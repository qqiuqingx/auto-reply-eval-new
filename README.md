# 客服自动回复质量评估流水线

这是一个仅使用 Python 标准库的可运行评估流水线。当前实现使用 `mock` 模式模拟评审模型返回，覆盖输入校验、按 `id` 关联、结构化返回校验、指标计算、风险标记、汇总和报告生成。

当前版本的定位是验证“读取数据 → 调用评审器 → 校验返回 → 计算指标 → 生成报告”这一整条链路。mock 分数是预先准备的模拟结果，不是程序理解自动回复后实时生成的判断，因此不能直接用于决定是否扩大自动回复覆盖范围。

## 运行

项目已包含本次的两份输入数据和 mock 响应，直接执行：

```bash
cd auto-reply-eval-new
python3 evaluate.py --mode mock
```

使用其他输入或输出目录：

```bash
python3 evaluate.py \
  --mode mock \
  --auto-replies /path/to/auto_replies.json \
  --human-ref /path/to/human_ref.json \
  --mock-responses /path/to/mock_judge_responses.json \
  --output-dir /path/to/artifacts
```

mock 响应必须覆盖输入中的全部 case id。缺少 case、字段、理由，或者出现 0～4 之外的分数时，流水线会失败并返回状态码 2，避免静默生成不完整报告。

## 指标定义及选择理由

业务方提出的“准确、有用、语气好、不能瞎编”被拆成四项可输出结构化结果的指标。由于当前没有真实订单、商品和政策证据，“准确”和“不瞎编”暂时通过“参考一致性 + 风险标记”表达，不能当作绝对事实判断。

| 指标 | 权重 | 量化方式 | 选择理由 |
| --- | ---: | --- | --- |
| 参考一致性 | 25% | 0～4分，检查自动回复是否与人工参考核心结论冲突、是否前后矛盾、是否包含参考材料无法支持的重要断言 | 当前只有人工回复可用于对照；将其命名为“参考一致性”可以避免把人工回复误当绝对真相 |
| 核心诉求完成度 | 40% | 0～4分，判断是否回答用户真正的问题、覆盖多个显式诉求、避免只给泛化知识 | 客服回复的首要价值是解决当前问题，因此设置最高权重 |
| 可执行性与服务主动性 | 25% | 0～4分，判断是否给出明确下一步、索取必要信息、主动查询或处理，而不是把任务重新推回用户 | 当前样本最明显的问题是“内容可能没错，但没有推进处理” |
| 场景化语气 | 10% | 0～4分，判断是否礼貌，以及是否对投诉、焦虑、故障、安全风险等场景作出合适回应 | 语气影响体验，但不能用礼貌掩盖错误、无依据或无用的回复 |

### 参考一致性

- 4分：与人工参考核心结论一致，没有明显冲突或重要风险断言。
- 3分：基本一致，但包含少量无法从当前材料核验的信息。
- 2分：存在重要无依据断言、流程矛盾或明显信息缺失。
- 1分：与人工参考的核心结论冲突。
- 0分：存在可能导致资金、账号安全或用户权益损失的严重错误。

该指标不等于事实准确率。例如 `case_03` 的银行卡退款时间、`case_18` 的30天质保以及 `case_19` 的自动提醒能力，都需要真实业务证据才能最终判断。

### 核心诉求完成度

- 4分：直接解决核心问题，或在信息不足时正确索取必要信息。
- 3分：给出主要答案，但缺少少量针对性内容。
- 2分：只有通用规则、部分回答或没有处理用户的具体问题。
- 1分：基本答非所问。
- 0分：完全无关或给出可能造成伤害的处理方向。

该指标不使用文本相似度。表达方式与人工回复不同，只要满足同样的用户目标，也可以得到高分。

### 可执行性与服务主动性

- 4分：直接处理，或索取完成处理所必需的信息。
- 3分：给出明确、低负担的操作步骤，并提供进一步协助。
- 2分：提供自助查询或处理路径，但主要工作仍由用户完成。
- 1分：只罗列原因、笼统建议或让用户再次寻找客服。
- 0分：没有任何可执行内容。

这一指标必须结合机器人真实能力解释。如果机器人没有查询订单的权限，未主动查询不一定是文案缺陷；反过来，如果机器人声称“我帮您查”但并未调用工具，也可能构成虚假承诺。

### 场景化语气

- 4分：礼貌自然，并能恰当回应用户的不满、焦虑或损失。
- 3分：礼貌清晰，但相对模板化。
- 2分：生硬、敷衍或与当前场景不匹配。
- 1分：指责用户、明显不耐烦或与用户争辩。
- 0分：侮辱、威胁、歧视等严重违规。

### 风险标记

四项分数之外，评审返回还可以包含 `low`、`medium`、`high` 三档风险，例如：

- 内部流程矛盾；
- 无法核验的退款、运费或补偿政策；
- 未经证明的系统能力；
- 虚构订单、物流、账号或退款状态；
- 可能影响资金、账号安全或用户权益的错误建议。

当前实现只统计风险标记，没有实施风险硬门槛。正式版本应规定：严重内部矛盾、虚构业务状态、虚构费用权益或虚构工具执行结果直接判为不合格并转人工，不能依靠其他指标拉高综合分。

### 综合分和等级

```text
综合分 =
  参考一致性 / 4 × 25
  + 核心诉求完成度 / 4 × 40
  + 可执行性与服务主动性 / 4 × 25
  + 场景化语气 / 4 × 10
```

- 85～100：优秀
- 70～84.9：合格
- 50～69.9：需要改进
- 0～49.9：不合格

这些权重和阈值是当前方案的初始口径，尚未经过多人标注和业务结果校准，不能解释为真实质量百分比。

## 评估方法

### 1. 输入关联和校验

流水线读取自动回复和人工参考两个 JSON 数组，按 `id` 一一关联，并检查：

- `id`、`user_question`、`auto_reply`、`human_reference` 为非空字符串；
- 两份文件内部没有重复 `id`；
- 两份文件的 `id` 集合完全一致；
- `annotator_notes` 如存在必须是字符串。

人工参考中的 `XX`、`<字段>`、`***` 等占位符只从具体事实比对中排除，不会使整条样本失效。以 `case_13` 为例，仍会正常评估是否主动提供成分、是否关照敏感肌诉求和回复语气。

### 2. 评审器调用

每条样本通过统一的 `JudgeClient.evaluate()` 接口评审。当前 `MockJudgeClient` 仅根据 case id 从 `data/mock_judge_responses.json` 读取固定模拟响应，再将其序列化成原始 JSON 文本，以模拟远程模型返回。

### 3. 返回校验

`parse_judge_response()` 对 mock 或未来真实模型的返回执行统一校验：

- 四项指标必须完整且不能多出未知指标；
- 每项分数必须是0～4的整数；
- 每项必须包含非空理由；
- `missing_points` 必须是字符串数组；
- 风险等级只能为 `low`、`medium` 或 `high`；
- 必须提供整体摘要。

不满足契约时流水线返回状态码2，不会静默生成部分报告。

### 4. 聚合和报告

校验通过后，流水线计算综合分和等级，并输出：

- 每项指标的平均分与分布；
- 综合分平均值和等级分布；
- 风险标记数量；
- 每条回复的理由、缺失要点和风险；
- 最低分的三条样本；
- 输入文件路径和 SHA-256。

当前20条 mock 结果的平均分为71.1，其中优秀3条、合格8条、需要改进7条、不合格2条。该结果是模拟评审数据的聚合结果，不是模型实时分析得到的质量结论。

## mock 返回契约

`data/mock_judge_responses.json` 模拟评审模型的 JSON 返回，每个 case 包含：

```json
{
  "metrics": {
    "reference_consistency": {"score": 4, "reason": "..."},
    "intent_completion": {"score": 3, "reason": "..."},
    "actionability": {"score": 2, "reason": "..."},
    "tone": {"score": 3, "reason": "..."}
  },
  "missing_points": ["..."],
  "risk_flags": [
    {"code": "...", "severity": "low|medium|high", "claim": "...", "reason": "..."}
  ],
  "summary": "..."
}
```

`MockJudgeClient` 会先把对象序列化为模型可能返回的原始 JSON 文本，再通过统一的 `parse_judge_response` 校验。接入真实模型时，实现相同的 `JudgeClient.evaluate()` 接口并复用该解析函数即可，汇总和报告逻辑不需要修改。

## 输出

- `artifacts/evaluation_results.json`：运行信息、指标定义、汇总和每条完整评审结果。
- `artifacts/evaluation_report.md`：适合人工阅读的汇总报告、逐条得分和最低分样本分析。

输出会记录两份输入文件的 SHA-256，便于确认报告对应的数据版本。报告会明确标注 mock 结果只用于验证流水线，不能直接作为扩大自动回复覆盖范围的依据。

## 可能评不准的 case

| Case | 不确定性来源 | 当前结果应如何解释 |
| --- | --- | --- |
| `case_02` | 缺少具体充电宝参数和正式航空规则 | 可以判断回复没有核对具体商品，但不能仅凭参考回复确认100Wh规则绝对准确 |
| `case_03` | 缺少退款渠道、订单状态和真实退款政策 | 只能确认没有查询用户的退款；3～7天、5～15天应标为待核验，不能直接认定错误或瞎编 |
| `case_04`、`case_18` | 缺少订单时间和真实质保政策 | 7天或30天质保、退换条件需要政策证据支持 |
| `case_08` | 人工备注称回复“不够有用”，但自动回复已经直接回答TPU材质 | 如果机械采信备注，会低估这条回复；当前按实际文本给出较高分 |
| `case_09` | 运费可能受商品、商家、原因和运费险影响 | 简化规则可能不完整，必须结合真实售后政策 |
| `case_10` | 不知道订单当前是否允许取消 | 可以评价操作说明是否清晰，不能确认本订单一定可以取消 |
| `case_11` | 回复内部存在两套换货流程，运费规则又缺少证据 | 流程矛盾可以确定；“买家承担运费”只能待核验 |
| `case_13` | 人工参考包含占位成分，缺少真实商品成分表 | 样本仍有效，但只能评估是否主动提供信息，不能比较具体成分事实 |
| `case_14` | 不知道系统是否确实支持商品视频 | “部分商品已支持视频”属于需要产品能力证据的断言 |
| `case_15` | 不知道补偿政策和机器人发券权限 | 自动回复和人工参考中的补偿表述都不能天然视为真实政策 |
| `case_17` | 包含两个诉求，并可能依赖前序订单上下文 | 自动回复实际覆盖了两个问题，机械使用人工备注可能低估它 |
| `case_19` | 不知道购物车是否具有补货提醒能力 | “系统会自动提醒”是高风险能力声明，但当前只能标记待核验 |
| `case_05`、`case_07`、`case_15`、`case_20` | 同理心和安抚力度存在主观性 | 不同客服规范、品牌语气和用户群体可能给出不同分数 |

此外，`case_01`、`case_03`、`case_06`、`case_07`、`case_12`、`case_17`、`case_19` 是否应该因为“没有主动查询”而扣分，取决于机器人是否具有相应工具权限。正式评估必须把可用能力作为输入。

## 当前局限性

1. **mock 不执行语义评估**：同一个 case id 即使替换了问题或回复文本，仍会得到原来的固定分数。
2. **mock 与输入内容没有逐条绑定**：目前只检查 case id，没有用内容哈希阻止过期 mock 结果被复用。
3. **人工参考不是事实库**：它能够表达期望服务方式，但不能证明退款时间、质保、运费、商品参数或系统能力真实有效。
4. **缺少完整上下文**：`这个充电宝`、`这款面膜`、`那两款手机`、`那个包`都可能依赖商品页面或历史对话。
5. **缺少机器人能力边界**：不知道机器人能否查询订单、查看登录记录、取消订单、发起售后、发券或设置提醒。
6. **单一参考不是唯一正确答案**：措辞不同但同样正确的回复不应因为文本不相似而扣分。
7. **语气评价具有主观性**：当前没有品牌语气规范，也没有多名标注员的一致性数据。
8. **高风险没有硬门槛**：`high` 目前只参与统计，不会自动覆盖综合分和等级。
9. **简单平均会掩盖风险**：普通材质咨询和涉及资金、账号安全的回复在汇总中权重相同。
10. **占位符识别有限**：目前只识别 `XX`、`<...>` 和连续星号，可能漏掉其他占位形式，也可能误判真实型号。
11. **没有真实模型调用治理**：尚未实现提示词版本、API重试、限流、并发、原始响应留存、成本和延迟统计、模型漂移监控。
12. **测试只验证工程链路**：现有测试能证明输入校验、计算和报告生成正常，不能证明评分符合真实客服质量。

## 后续优化

### 第一阶段：完善标注和能力数据

将一段自由文本人工回复拆成结构化金标：

```json
{
  "id": "case_03",
  "intent": "查询具体退款进度",
  "required_points": ["索取订单号", "查询实际退款状态"],
  "optional_points": ["说明一般退款时效"],
  "verified_facts": [
    {
      "claim": "支付宝或微信退款一般1-3个工作日",
      "source": "退款规则V3.2"
    }
  ],
  "forbidden_claims": ["未查询订单就声称退款已经到账"],
  "available_actions": ["query_refund_status"],
  "emotion": "neutral",
  "risk_level": "high"
}
```

同时为 mock 响应保存输入内容哈希；问题、回复或参考内容变化后，旧的模拟结果必须失效。

### 第二阶段：接入真实业务证据

评审输入补充当时版本的知识库、商品参数、订单/物流/退款状态、政策、机器人可用工具以及真实工具调用结果。将回复拆成原子事实，分别判断：

```text
有证据支持 / 与证据矛盾 / 无法验证
```

无法验证不应直接判错，应进入风险标记或人工复核队列。

### 第三阶段：接入真实评审模型

用真实模型实现 `JudgeClient`，要求每项评分引用自动回复原文和结构化金标/业务证据。补充提示词版本管理、超时重试、限流、并发、原始返回留存、失败重评、成本和延迟统计。

### 第四阶段：人工校准

按业务类型、风险等级和是否需要工具调用进行分层抽样，由至少两名客服独立评分，对分歧样本仲裁，并计算标注一致性、模型与人工的混淆矩阵以及各类问题的准确率和召回率。`case_08`、`case_13`、`case_17` 应作为重点校准样本。

### 第五阶段：风险门槛和分层报表

将虚构业务状态、虚构费用权益、虚构工具执行结果和关键流程矛盾设为硬门槛；同时按咨询、售后、投诉、账号安全，是否涉及资金，是否需要工具调用等维度分别报告，并展示样本量和置信区间，避免总平均分掩盖低频高风险问题。

### 第六阶段：结合线上业务结果

在影子模式和小流量阶段，将文本评分与重复咨询率、转人工率、一次解决率、投诉率、用户满意度及资损事件结合，持续修正权重和阈值。推荐推进顺序为：

```text
mock 验证流水线
→ 人工金标校准
→ 真实模型影子运行
→ 人工抽检
→ 小流量使用
→ 持续监控
```
